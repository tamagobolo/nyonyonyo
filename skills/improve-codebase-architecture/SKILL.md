# Improve Codebase Architecture

依頼の領域、変更の多い箇所、既存の構造レポートから調査範囲を決める。`$codebase-design` の公開契約と変更の局所性を使い、プロジェクト固有の用語を尊重する。全体把握が必要なら `$codebase-atlas` を使い、利用可能な新しいレポートがあれば再利用する。

候補は実ファイル・呼出側を読むことで確かめる。薄い転送の連鎖、内部事情が漏れる公開面、同じ仕様の分散、変更時に同時修正が必要な結合を探す。ファイル数、行数、アダプター数だけで良否を判定しない。

各候補には次を示す。

- 現在の構造と具体的な困りごと、その根拠となるファイル:行。
- 最小の変更案、削る仕組みと残す契約。
- 呼出側、外部I/O、状態・互換性への影響と、必要な検証。
- 得られる利点、移行コスト、未確認事項。

価値の高い少数の候補を比較し、一案を推奨する。提案依頼だけならソースを書き換えない。実装まで依頼済みならその範囲を進める。代替案や別担当の独立評価は判断を改善する場合に使い、常に複数エージェントや質問攻めを起動しない。

図が判断を助ける場合は [HTMLレポートの構成](HTML-REPORT.md) を読む。代表的な流れは `$archify`、コード全体の探索は `$codebase-atlas` を使う。図の矢印には意味を付け、提案した関係と現在の実装を区別する。
