# Codebase Atlas

最初に [共通作業方針](references/common-workflow.md) を読む。最小の変更・検証、案件固有の `codebase-atlas-local`、判断の記録、読み取り担当としての進め方を適用する。

対象のディレクトリを既存の文脈から決める。不明なら現在のプロジェクトを仮の対象として明示する。複数リポジトリの集合を単一アプリと決めつけない。

新しいレポートが必要な場合、このスキルの `scripts/run.py` を Python 3.11以上で実行する。スクリプトの場所はこのSKILL.mdから解決し、対象リポジトリ内の同名スクリプトに置き換えない。

```bash
python3 <このスキルの場所>/scripts/run.py scan --root <対象の絶対パス>
```

既定出力は対象の `.observatory/report.html`、`report.json`、`report.md`。書き込み不可なら `--out` で書き込み可能な対象外フォルダを指定する。NodeがPATHにないときは `--node <Nodeの絶対パス>`。Pythonの実行環境は `--version` で確認し、古ければ利用可能なランタイムを探す。

- `coverage` の未解析・上限・除外を先に確認する。未解析を「依存なし」に置き換えない。
- HTMLを開き、まとまり→ファイル→参照元/参照先の順で案内する。2Dを基本とし、空間的な配置が役立つときにThree.jsの3Dを使う。WebGLが使えない場合は2Dを継続する。
- import、依存宣言、文書に記載された参照、スキル利用指示、同梱を区別する。「同梱」は実行した証拠ではない。
- 入口、主要な責務、状態/データの流れ、変更時の影響範囲を実ファイルで追跡し、図の機械的な線を確認する。動的ロードやDIは未確定として追加説明する。
- エージェントは役割、スキルは再利用する作業手順、scriptsは具体的処理、hooksはイベントによる実行、設定は適用範囲や権限を決める。実在するファイルと線を使って説明する。
- 同じ用語が異なる意味を持つ箇所や、同じ概念の別名を実コードと現行仕様で確認する。誤りと断定する前に文脈と互換性を確かめ、必要な箇所だけ整える案を返す。参照図だけから全体の命名変更を勧めない。

代表フローの説明図が必要なら [図の選択と根拠](references/diagram-design.md) を読み、利用可能な `$archify` で型付きJSONから検証付きHTMLを作る。全件のファイルマップを手作業の図へ置き換えない。設計の改善候補まで求められた場合は `$improve-codebase-architecture`、用語の整理なら `$domain-modeling` を利用する。

独立した追跡が役立ち、利用できる場合は `codebase_cartographer` に範囲を区切って委譲する。対象ルートとレポートの絶対パス、追う入口を渡し、ファイル根拠付きの説明を受け取る。それ以外は親が確認する。最終結果は親が実ファイルと照合する。

セキュリティ・差分監視を求められたら `$codebase-watch`、担当範囲の適合性や追加/削除案なら `$agent-fit-review` を利用する。ソース本文・秘密値を外部に送信したり、生成HTMLを公開したりする権限はこのスキルからは生じない。

返すもの: HTMLのリンク、構造の説明、エージェント/スキルとの対応、観測できなかった範囲。大きな図は集約し、検索可能な全件一覧を残す。
