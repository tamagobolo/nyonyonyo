# Codebase Design

対象のAGENTS.md、仕様、用語集、実際の呼出側を先に確認する。既存の「サービス」「API」などの用語を尊重し、ここでの語彙は分析の補助として使う。

- **深いモジュール**: 小さく理解しやすい公開面に、意味のある処理と不変条件を隠す。ファイルの長短だけで判断しない。
- **公開インターフェース**: 入出力だけでなく、失敗、順序、状態、互換性を含む呼出側との契約。
- **境界とアダプター**: 変更理由、外部I/O、所有権、検証の必要性で選ぶ。実装が一つでも契約や隔離に価値がある場合は残す。
- **変更の局所性**: 一つの仕様変更がどのファイルへ波及するかを、実際の参照と責務から説明する。

公開面と実装がほぼ同じ薄い転送、内部事情の漏れ、同時変更が必要な分散を候補にする。「この層を除くとどの契約・責務が失われるか」を調べ、意味がないと確認できた部分だけ統合を検討する。静的参照が見つからないだけでは削除しない。

実装では既存コード→標準機能→導入済み依存→最小の独自処理の順で検討する。予想上の拡張点を先に作らない。振る舞いを守る最小の検証を行い、構造の変更に追従するだけのテストを増やさない。

統合を具体化するときだけ [依存と検証](DEEPENING.md) を読む。複数案の比較を依頼された場合や大きいトレードオフがある場合は [代替案の比較](DESIGN-IT-TWICE.md) を使う。小変更で複数案・委譲・新規文書を必須にしない。

結果には対象ファイル、現状の困りごと、最小の提案、守る契約、検証と残る懸念を示す。重要な用語の不一致は `$domain-modeling`、全体の候補探索は `$improve-codebase-architecture` を必要に応じて使う。
