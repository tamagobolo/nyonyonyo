# TDD

既存の仕様、公開インターフェース、テスト基盤を読む。会話で承認済みの仕様や境界は引き継ぐ。振る舞いが変わる未確定事項だけ確認し、各テストの前に改めて承認を要求しない。

一つの利用者・呼出側に見える振る舞いを縦に完成させる。

1. **Red**: 既知の入力・独立した期待結果でテストを書き、目的の理由で失敗することを確かめる。実装と同じ計算を期待値へ複製しない。
2. **Green**: その振る舞いを満たす最小の実装を行い、関連テストを通す。将来用の抽象化や網羅的な先行実装を足さない。
3. **Refactor**: 重複や漏れた責務が具体的にある場合に整える。影響範囲に応じた検証を行い、次の振る舞いへ進む。

公開契約から検証し、内部メソッドの呼出回数や私有状態への依存を避ける。ただし順序・回数が外部契約ならその契約を検証する。詳細は [良いテストと悪いテスト](tests.md)、外部I/Oを置換する必要がある場合は [モックの境界](mocking.md) を読む。

テストはユーザーに必要な保証のために置く。文書・表示文言など低影響で可逆な変更に形式だけのテストを追加しない。フルテストは広い影響、関連テストの失敗、プロジェクトの明示要件があるときに絞り、各サイクルで機械的に回さない。
