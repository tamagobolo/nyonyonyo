# Ponytail Review

対象の差分、呼出側、プロジェクトの規約と依存を読む。要求された振る舞いと互換性・失敗時の契約を確かめてから、次の候補を探す。

- 既存機能と重複していて一本化できる処理。
- 標準ライブラリ、プラットフォームの機能、導入済み依存で代用できる独自処理や新規依存。
- 現在の利用例や制約を支えない設定、拡張点、ラッパー。
- 同じ保証をより理解しやすく表せる分岐やデータの持ち方。

各候補はファイル:行、不要と判断できる証拠、小さい代案、変わる契約と確認方法を示す。参照が見つからないことだけを未使用の証明にしない。公開API、動的登録、テスト用隔離、監査上の責務を調べる。実装一つ・行数が多いという理由だけで削除しない。

簡素化で入力検証、権限制御、データ保護、アクセシビリティ、エラー報告を弱めない。正しさの欠陥が見つかれば複雑さの問題と分けて報告する。一般的な仕様・欠陥レビューが必要なら `$code-review` を使う。

レビュー依頼では提案までとし、修正を依頼された場合だけ変更する。候補がなければ無理に削減案を作らない。行数差は具体的な差分から測れた場合だけ添え、コストや速度の効果は計測なしに保証しない。
