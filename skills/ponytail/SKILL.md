# Ponytail

要求される振る舞いと守る契約を押さえ、関係する実装・呼出側・テストを読む。次の順で十分な解決策を探す。上の段階で要件を満たせれば、下の仕組みを追加する必要はない。

1. 既存コードの機能、共通部品、確立したプロジェクト内の方法。
2. 標準ライブラリ。
3. 言語・フレームワーク・プラットフォームの標準機能。
4. すでに導入済みの依存。
5. 要件に必要な最小の独自処理。新規依存が有利なら、既存方法で不足する具体的な理由と保守負担から判断する。

仕組みの削減は、仕様、公開契約、読みやすさ、失敗時の扱いを保って行う。信頼境界の検証、認証・認可、データ保護、アクセシビリティを行数のために削らない。短い正規表現や一行式への置換が同じ振る舞いかは別途確かめる。

抽象化・設定・汎用化・フォールバックは、現在の利用例や制約を理由に置く。将来あるかもしれない利用者のためだけに増やさない。小さい転送でも互換性や隔離の契約があれば保持する。

必要な変更を実装し、影響する最小の検証を行う。フルテストを繰り返したり、コードと同じ計算を写すテストを追加したりしない。結果には再利用した箇所と、残した独自処理の理由を必要な範囲で示す。削減行数やトークン節約を測っていなければ数値で主張しない。

既存の差分だけを精査する場合は `$ponytail-review` を使う。この配布版は再利用手順を提供し、Ponytail上流の常時注入Hookやモード切替用の状態管理は含めない。
