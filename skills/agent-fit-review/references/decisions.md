# 追加・統合・廃止の判断

|判断|必要な根拠|次の一手|
|---|---|---|
|維持|現行のワークフローを支え、入力/出力・権限が妥当|代表的な実作業で確認|
|既存を拡張|担当範囲は合うが技術・チェック項目が不足|不足分だけ追加し適用範囲を保つ|
|新規追加|反復する作業/リスクの担当がなく、既存への追加では責務が混ざる|具体的な起動条件と成果物を定義|
|統合|同一手順または重複責務があり、範囲・権限・利用者も整合|呼び出し元、別名の用途、適用階層を確認|
|廃止候補|役割が消失または代替済みで、手動/暗黙/他プロジェクトからの利用も不要と確認|参照元を移行し、復元可能な形で無効化を試す|
|判断保留|参照がないだけ、利用実績なし、適用スコープが不明|利用者・最近の作業・適用クライアントを確認|

任意に選んだ「30日未使用」などの閾値だけで削除しない。セキュリティや障害時の担当は利用頻度が低くても必要な場合がある。スキルの選択用descriptionと、エージェントの役割/権限は別々に評価する。

hooksや設定では「存在」「参照される」「有効」「信頼済み」「実行された」を区別する。起動ログがなければ後二者を断定しない。カスタムエージェントのnameがbuilt-inと衝突する場合や、同名スキルが複数スコープにある場合は優先関係を確認する。

## 判断基準を置く場所の適合性

- スキルには再利用する手順と判断基準、エージェントには呼出先・入出力・独立性・権限を置く。知識が複数エージェントへ重複していれば、既存スキルへの集約を先に検討する。専門分野があるだけで新しい担当を増やさない。
- 共通の手順と `*-local` の差分が分かれているか、片方を直すときに全コピーの更新が必要になっていないかを見る。`-local` がないこと自体は問題にしない。別案件の業務規則を共通へ持ち込まない。
- 判断基準、結果を確かめるテスト/観測、操作の権限/hook等の制約の3つが、主要ワークフローでどの実ファイルに対応するかを確認する。静的レポートだけで実行時の強制力を認定しない。
- レビュー由来のルールに出典と適用条件があるか、現行仕様と過去の判断が区別されているかを確認する。却下案を現行仕様として復活させない。
- モデルや標準機能の改善で前提が変わった補助機構は、同じ代表入力と合格条件で必要性を比較する。構成を減らす目的で、必要なテスト・観測・権限制約を削除しない。比較が未実施なら廃止判断は保留する。
