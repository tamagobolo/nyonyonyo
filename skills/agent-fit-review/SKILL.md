# Agent Fit Review

最初に [共通作業方針](../codebase-atlas/references/common-workflow.md) を読む。最小の変更・検証、案件固有の `agent-fit-review-local`、判断の記録、読み取り担当としての進め方を適用する。

現在の構造と制御ファイルを取得する。既存の新しいObservatoryレポートがあれば観測範囲と取得時刻を確認して使い、なければこのスキルの `scripts/run.py scan --root <対象>` をPython 3.11以上で実行する。

コード、採用技術、主要ワークフロー、変更頻度、実際の失敗・利用実績と、スキルのdescription/手順・エージェントの責務/権限を突き合わせる。必要な場合だけ `--context-root <実際に適用される追加定義のフォルダ>` を加える。無関係な個人スキルを、そのリポジトリで使わないという理由だけで削除候補にしない。

独立した評価が役立ち、利用できる場合は `agent_fit_reviewer` にコードの主要な入口、レポート、現行定義、実績がある場合はその情報を渡し、範囲を区切った適合性評価を依頼する。それ以外は親が同じ確認を行う。

判断基準は [references/decisions.md](references/decisions.md) を読む。自動検出は構文・参照・明示語句の点検であって、最適性の証明ではない。利用実績がなければ「未取得」とし、架空の利用率やスコアを作らない。

スキルの起動条件・手順・参照・実効性を点検する場合は [スキル自体の品質](references/skill-quality.md) も使う。コード差分の過剰設計を調べる場合は `$ponytail-review`、仕様とコード規約への適合は `$code-review` に役割を分ける。

提案ごとに、対象パス、現状の問題、コード上の根拠、追加/拡張/統合/廃止の選択理由、代替先、確認すべき影響、検証方法を記載する。追加案には適切なskill名/agent名と短い責務を付ける。削除案は「不要と確認済み」と「使用実績の確認待ち」を分ける。該当がなければ「今は削除を勧める根拠なし」とする。

対象はSKILL.mdとagentのTOMLだけに限定しない。支援scripts、hooks、.js/.mjs/.cjs、.toml、.tol、YAML/JSON、CI、MCP/rules設定の参照元・起動条件・権限・責任者まで確認する。

レビュー依頼は提案まで。変更も依頼されている場合は既存の権限を確認し、参照元と関連文書を同時に更新し、動作を検証する。
