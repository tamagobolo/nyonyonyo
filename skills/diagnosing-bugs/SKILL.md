# Diagnosing Bugs

期待した結果、実際の結果、発生条件、最初に起きた時点を、既存の会話・ログ・差分から集める。すでにある情報を質問し直さない。観測を一つの検証可能な失敗として表す。

1. 関連する入口、呼出側、状態、最近の変更を読む。比較できる正常例があれば失敗例との差を調べる。
2. 最小の入力と手順で再現する。既存テストや診断機能を先に使う。再現できない場合も、読み取りで絞れる範囲を進め、未確認の条件を記録する。
3. 観測を説明する仮説を優先順に置く。各仮説が正しければ何が変わるかを決め、一度に一つの条件を変える。計測や試行回数は識別に必要な範囲だけ増やす。
4. 原因を確かめたら、依頼の範囲で最小の修正を行う。症状だけ隠す例外握りつぶしや無制限リトライを加えない。
5. 元の再現と影響する周辺の振る舞いを確認する。再発防止に価値がある動作には回帰テストを残す。変更も新しい懸念もなければ通ったテストを繰り返さない。

ユーザー操作が不可欠な再現では、手順を短く具体化する。[対話式再現のひな型](scripts/hitl-loop.template.sh) は必要な場合だけ対象用にコピー・編集して使う。無編集で実行せず、認証情報や生の個人情報を収集しない。

報告には症状、裏付けた原因、修正、実際の検証、残る不確実性を含める。仮説だけの場合は原因確定と表現しない。
