# Domain Modeling

既存のAGENTS.md、仕様、用語集、CONTEXT.md / CONTEXT-MAP.md、判断記録を先に探す。会話で確定した情報を再質問せず、残る不明点のうち設計や意味を変えるものだけ確認する。

1. 今回の操作・出来事を具体例で追い、登場する概念、識別子、状態遷移、制約を集める。
2. 同じ語の別義、同じ概念の別名、実装と仕様の不一致をファイル位置とともに示す。異なる部門やコンテキストで別義が必要なら無理に統一しない。
3. 概念の定義と所有する責務、コンテキストを越えるデータやイベントを整理する。現状の観測と提案を分ける。
4. 依頼に含まれる文書更新を既存形式で行う。既存文書で足りるなら新規ファイルを作らない。名称整理だけで公開APIや永続データを一括変更しない。

用語集が必要で形式がない場合だけ [CONTEXTの記入例](CONTEXT-FORMAT.md) を使う。複数コンテキストが実在するときに関係図を追加し、将来の仮想分割は作らない。重要な仕様・設計の決定には、既存のRDR/ADRを優先し、なければ [短いADR](ADR-FORMAT.md) を使う。

結果は、今回定まった用語と不変条件、コード・文書への影響、未解決の判断を示す。更新した文書の参照と意味の整合を確認し、文書修正だけでフルテストを起動しない。
