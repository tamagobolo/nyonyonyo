# 点検の根拠と限界

## 優先順位

1. 読取エラー、範囲の変化、パーサー未導入を直し、観測できた範囲を確定する。
2. 秘密値候補、権限迂回、TLS無効化、外部取得コードの即時実行、コマンド注入/XSS候補の入力源を追う。
3. `.codex/agents/*.toml`、`SKILL.md`、`agents/openai.yaml`、hooks.json、inline `[hooks]`、package scripts、CI定義、MCP/rules、`.js/.mjs/.cjs/.ts` を確認する。
4. `.tol` はそのままインベントリに含め、参照元と用途を確認する。`.toml` の誤字と断定しない。
5. importや責務、使用技術の変化を担当スキル/エージェントの範囲へ反映する。

## 静的検出の後に確認すること

- 候補のコードは本番で使われるか、外部入力が到達するか、認証・認可・サニタイズはどこにあるか。
- hooksはどのイベント/条件で起動するか、実行される.js/.sh/.pyは何か、外部通信/機密アクセス/書き込み権限は必要か、タイムアウト・失敗・再帰・並列実行をどう扱うか。
- Gitの `core.hooksPath`、worktreeの共有hooks、ホーム設定、MCPやプラグインの設定は対象外にあり得る。必要な場所を読み取りで特定し、`--context-root` を明示して追加する。ホーム全体を対象にしない。
- Codexのhooksは信頼確認された定義だけが実行される。ファイルが存在することと、登録・信頼済みで実行されていることを区別する。
- 脆弱な依存の確認では対象のlockfileと使用中のパッケージマネージャーを確認する。例えば既存のnpm lockfileで `npm audit --json --ignore-scripts` を実行するときは、依存情報をレジストリへ送ることを考慮する。未実行・ネットワーク失敗を脆弱性0件と報告しない。pip-audit、OSV、Semgrep、gitleaks等も既存の環境に合わせ、未導入のツールを実行済みとしない。

## 報告

確定した構文不備と、到達性未検証の危険な処理を区別する。秘密値を引用せず、ルール名とファイル:行を示す。誤検知は除外理由を残して扱い、ルールを一律に無効化しない。差分のIDには行番号を含むため、行移動が見かけの新規/解消を作り得る。

## 個人情報保護の3段階を点検する

対象の現行ルールで、個人情報・機密に該当する分類と公開先を確かめる。ルールがなければ未定義として報告する。顧客データを点検例へコピーせず、検証には合成データを使う。

|段階|確認する根拠|
|---|---|
|commit/PR等の公開前|対象差分、本文、ログ、添付物に適用される既存の検査とマスキング規則。hookの起動条件・失敗時の扱い・迂回可能性|
|CIでの検出|実際のCI定義と直近の実行結果。何を検査し、何を止めるか、検査失敗/未実行が成功扱いにならないか|
|混入後の対応|共有の停止、混入先の特定と除去、必要な連絡先、認証情報なら失効/再発行等の既存手順。履歴修正など不可逆な操作は対象と権限を確認|

各段階は「実行を確認」「定義のみ」「未導入」「観測範囲外」に分ける。定義の有無は読むだけで点検できる。挙動の確認が必要なら、対象の権限内で該当する最小の既存テストを選ぶ。PIIを含む本物のPRを試しに作らない。

指摘には分類と位置を使い、PIIや秘密値そのものを再掲しない。公開先で識別可能なファイル名も伏せる。このスキャナの秘密値ルールはPIIの網羅検査ではなく、3段階のhook/CI/復旧機構を新設・有効化するものでもない。不足する場合は、既存の仕組みに補う具体案を返す。
