# ブログと写真から取り込んだ要件

2026-09-10に、指定された [AI-Native な開発の実践に向けて — メルカリエンジニアリング（2026-06-30）](https://engineering.mercari.com/blog/entry/20260630-b22667b4d6/) の本文と個人情報保護の図を確認した。以下は記事全文の転載ではなく、この共通ツールへの適用内容である。

## 共通ツールへの反映

|採用した観点|このツールでの扱い|
|---|---|
|機構と判断基準を分離|既存のCLI・権限機構を使い、正解・合格・危険の根拠を対象の文書へ結び付ける|
|共通と固有を分離|共通の3スキルと、必要な案件だけで追加して読む `*-local` の規約。自動上書き機構は作らない|
|スキルに知識、エージェントに役割|3エージェントを呼出先・入出力・読み取り権限に整理し、判断手順はスキルの参照文書へ集約|
|用語と判断を一貫させる|構造調査で名称と意味を確認。現行仕様・設計とRDR/ADRを分け、レビューから得た基準を適切な共通/固有の置き場へ反映|
|再現可能な検証|既存スクリプトで入力と期待結果を確かめる。写真の要望に合わせて実行範囲と再実行の条件を絞る|
|個人情報を複数段階で保護|公開前・CI・混入後の対応を監視スキルの点検項目に追加。原文を指摘文へ複製しない|
|継続可能な記録|長い作業は既存planに進捗と検証結果を残し、必要なら `TODO.local.md` を利用|

実際の手順は [共通作業方針](../skills/codebase-atlas/references/common-workflow.md)。案件側に記入するための [判断基準](../examples/project-context.md) と [RDR/ADR](../examples/decision-record.md) の例も用意した。

記事のNotion同期、GitHub Actionsからの実装、特定の業務ルールは各案件の構成に依存するため、このツールの必須機能にはしていない。sessionのforkは記事中の個人的な運用観として扱い、進捗を持ち運べるファイルに残す点を採用した。フルテストを減らす方針は下の写真に由来する。

これはスキルの作業手順・点検項目の拡張であり、PIIの自動検出器やcommit/PRを止めるhookを新設したという意味ではない。静的スキャンだけでは、それらの実行状態や網羅性は証明できない。

## 写真の内容

提供された「写真1.jpg」の文章を、画像中の折り返しだけ除いて記載する。

> オーバーエンジニアリング禁止を明示してなさそうだな。AGENTS.mdとかで、最小の検証で回すようにしてフルテストの回数を減らしてオーバーエンジニアリングを避ける指示を2行くらい入れておくといい感じになるかもしれん。

[AGENTS.md](../AGENTS.md) と共通作業方針に、次の2行を反映した。

```text
オーバーエンジニアリングを禁止する。要求を満たす最小の変更を選び、不要な抽象化・依存・仕組みを追加しない。
検証は変更の影響に必要な最小範囲から行う。フルテストは広い影響・失敗・明示要件がある場合に絞り、変更や新たな懸念がなければ繰り返さない。
```

この `AGENTS.md` はツール自身への作業指示。別のコードベースでは3スキルが共通作業方針を読むことで同じ方針を適用する。ほかのリポジトリの `AGENTS.md` を一括変更する必要はない。
