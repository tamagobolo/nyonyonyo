01 / はじめにMarkdown 原本 ↗

ワークスペース開発ガイド v1

このガイドは、複数のプロジェクトを同じローカルワークスペースで扱い、Codex と共同で開発するチームのための資料です。作業対象を特定し、根拠を集め、変更・検証・共有まで進める方法をまとめています。共有先は tamagobolo/nyonyonyo、本版の格納場所は v1/ です。

初版資料は既存の場所に保存したまま、本版を追加しています。v1 は資料のフォルダ名です。Git タグや GitHub Release の作成を意味しません。

最初に読む場所

読み手 読む順番 読んだ後にできること
マネージャー ワークスペースの地図 → 作業フロー 対象、目的、範囲、受入条件を決めて依頼する
開発者 ワークスペースの地図 → 作業フロー 適用ルールと既存コードを確認し、小さく実装・検証する
新しく参加したシニア 90分の導入 → 指示文集 実装の入口と影響範囲を説明し、検証可能な指示を出す
導入・保守担当 スキルの設計 → 導入と保守 3つのスキルを適切な対象に配置し、資料を更新する

検索・コピーができる HTML ガイド は、このフォルダ一式を取得してブラウザで開きます。本文はオフラインで読めます。GitHub の通常のファイル画面では HTML は実行されません。上位フォルダの実コードへの参照もたどる場合は、リポジトリ全体を取得してください。

このワークスペースで守る3つの前提

  1. ワークスペースと Git リポジトリを分ける。 ローカルの親フォルダは複数プロジェクトを置く場所で、親全体が一つの Git リポジトリではありません。変更先・実行するディレクトリ・アップロード先を依頼ごとに合わせます。
  2. 配置されていることと、利用可能であることを分ける。 スキルの原本、読み込まれたスキル、エージェントの設定、実行権限は別々に確認します。
  3. 実ファイルの事実と提案を分ける。 このガイドの運用はチームへの提案です。実際の AGENTS.md、依頼、仕様、既存の検証・公開手順を読み、対象に合わせて使います。

図は マネージャー と 開発者 の2種類です。図の文章は日本語、拡大・検索・テーマ切替など固定の Viewer UI と HTML の言語属性は英語です。本文の手順と合わせて読みます。

3つのスキルは、紹介記事の着想をこのワークスペース向けに独自に再構成したものです。記事執筆者の公式実装や、確認済みの上流 GitHub スキルとしては扱いません。出典と確認範囲 に経緯を記載しています。

今日から始める

本版のスキルを使う場合は 導入手順 を先に確認してください。v1/ に置かれたスキルが、ワークスペース全体に自動で有効になるわけではありません。

02 / ワークスペースの地図Markdown 原本 ↗

ワークスペースの地図と作業の前提

どこで作業し、どこへ保存するか

このローカル環境では、親のワークスペースに複数の独立したプロジェクトがあります。共有資料の保存先は tamagobolo/nyonyonyo です。親フォルダ全体を公開する構成ではありません。公開資料では個人の絶対パスを使わず、次の相対表記を用います。

〈workspace〉/                  ローカルで複数の案件を置く親。Git リポジトリではない
├── 〈対象プロジェクト〉/       日々の開発対象。独自の Git・ルールを持つ場合がある
└── nyonyonyo/                 共有先 tamagobolo/nyonyonyo のチェックアウト
    ├── AGENTS.md              このリポジトリの基本方針
    ├── obs / observatory.py   Codebase Observatory の入口
    ├── src/ / viewer/         解析・レポート生成・画面
    ├── skills/ / agents/     共通スキルとエージェントの配布用原本
    ├── design/                System Atlas アプリ
    ├── ponytail/              取り込まれた外部プロジェクト
    ├── SAPGUI/                別の実行環境を前提とする専用手順
    └── v1/                    本ガイド。独立した Git リポジトリではない

別フォルダにある同名プロジェクトと、共有先に格納されたコピーを混同しないでください。依頼には「編集元」「共有先」「対象パス」を書きます。コピーする場合は編集元のコミットと共有先の保存位置も記録します。

開始時に確認すること

対象フォルダへ移動して実行します。結果を見てから変更に入ります。

pwd
git rev-parse --show-toplevel
git remote -v
git branch --show-current
git rev-parse HEAD
git status --short

Git の確認が失敗する場合は、そのフォルダが管理対象の外なのか、作業場所が違うのかを調べます。失敗を理由に新しい Git リポジトリを作ったり、親フォルダをまとめて追加したりしません。既存差分があれば依頼対象との関係を確認し、他者の作業を保持します。

ルール・スキル・実行手段の役割

要素 役割 このワークスペースでの確認
AGENTS.md / AGENTS.override.md 対象の作業方針、検証、禁止事項を伝える リポジトリから作業フォルダまでの適用ファイルと、編集先の下位ルールを読む
SKILL.md 特定の仕事の進め方と、使う条件を定義する 原本パス、名前、説明、実際の利用可否を確認する
agents/ などの設定原本 分担する役割や設定を配布する ファイルが存在するだけで、その役割が登録済みとは判断しない
CLI・ブラウザ・接続済みアプリ ファイルや外部サービスを読み書きする 認証、実行対象、書込み範囲、ユーザーの依頼を照合する
チェックや CI 定めた条件に対する検証結果を返す 何を検証したか、実行基準、未確認範囲を記録する

Codex の公式仕様では、プロジェクトの指示は通常 Git ルートから作業ディレクトリまでの経路をもとに読み込まれます。兄弟プロジェクトや下位フォルダにあるすべての指示が、親を開くだけで一括適用されるものではありません。対象の指示が読み込まれているかを確認します。公式：AGENTS.md

本リポジトリの方針は「要求を満たす最小の変更」「影響に必要な検証」です。今回の文書追加だけで、無関係なアプリの全面改修やフルテストを追加する理由にはなりません。実ファイル：AGENTS.md

リポジトリ内の入口と確認コマンド

以下は基準コミットのファイルで確認した定義です。本ガイド作成時に、アプリや全テストの動作を実行確認した一覧ではありません。

作業対象 / 実行場所 入口 定義されているコマンド・条件
Observatory / nyonyonyo/ obs → observatory.py ./obs test または npm test。Node.js 20以上、Python 3.11以上が定義されている
解析 / nyonyonyo/ src/scanner.py、scripts/js-analyze.mjs ./obs scan --root 〈対象〉 --out 〈出力先〉。解析結果を書き出す操作なので対象と出力先を指定する
レポート画面 / nyonyonyo/ viewer/main.jsx、viewer/style.css npm run build が assets/ の画面資産を生成する。ソースと生成物の関係を確認する
System Atlas / nyonyonyo/design/ package.json、当該 README npm run lint、npm run typecheck、npm test、npm run build。Node.js 24以上
外部取り込み / nyonyonyo/ponytail/ 当該 README、LICENSE 元の仕様とライセンスを保持し、変更内容に合う手順を選ぶ
SAP GUI / nyonyonyo/SAPGUI/ 当該 README、AGENTS.md Windows・SAP GUI を前提とする。ローカル macOS の確認で業務動作まで合格としない
本ガイド / nyonyonyo/v1/ README.md、scripts/build-guide.mjs Markdown・リンク・スキル定義・HTML表示を確認する

npm test の意味は実行場所で変わります。別プロジェクトのコマンドを、そのまま現在の場所で使わないでください。依存導入・ビルド・解析による生成物も変更差分として把握します。

実装の理解に必要な最短の流れ

Observatory の構造を読む場合は、次の順序が入口です。これは静的なソース確認に基づく関係です。

obs
  → observatory.py：引数、対象・出力先、scan / watch / compare / test の分岐
  → src/scanner.py：ファイル解析と関係・検出事項の集約
       → scripts/js-analyze.mjs：JS / TS の解析
  → src/reporting.py：JSON・Markdown・HTML の生成
       → assets/viewer.js・viewer.css：HTMLへ組み込む画面資産
            ↑ scripts/build.mjs が viewer/ から生成

処理を変更するときは、入口、公開される出力形式、例外時の挙動、既存テストをつなげて読みます。既存の構造説明 と 新任シニアの読み方 を参照してください。

03 / マネージャーMarkdown 原本 ↗

マネージャーの作業フロー

目的は、開発者が対象と完了条件を取り違えずに着手でき、結果を受け入れられる依頼にすることです。資料の枚数や会議を増やすことは目的に含めません。小さな変更では依頼本文だけで一連の判断を記録できます。

対話型フロー図を開く

1. 目的と対象を決める

変更依頼 に「誰の、どの場面の問題か」「成功を何で判断するか」「編集先と共有先」「今回の対象外」を書きます。プロジェクト名だけでなく、リポジトリと相対パスを記します。

このワークスペースでの例は「新しく参加したシニアが、対象コードと検証方法を特定して最初の指示を出せること。保存先は tamagobolo/nyonyonyo/v1/、既存版は保持」です。「分かりやすくする」だけの依頼から、読者の行動と成果物を判定できる依頼へ具体化します。

2. 必要な視点を使って案を比べる

スキル 問うこと 残す結果
$workspace-persona マネージャー、開発者、新任シニアで何に迷うか 読者ごとの課題・成功条件・必要な情報
$workspace-detour 新規実装以外の方法で目的を満たせるか 現状維持、既存機能の活用、資料改善、小さな実装の比較
$workspace-thriller 最初の一回で、どの行動が成功すれば役立つと分かるか 最重要の利用場面と、その確認方法

すべてを毎回呼び出す必要はありません。対象の配置と使い方は 導入手順 を確認します。人物像は調査済みの事実と仮定を分け、スキルが出した案は採用するまで候補として扱います。

3. 範囲と受入条件を確定する

受入条件には、観測できる結果を付けます。資料なら「リンクが開く」「指示文に対象・完了条件がある」、機能なら「この入力にこの出力を返す」「失敗時にこの状態を保持する」などです。優先順位と対象外も合わせて技術責任者へ渡します。

判断の地点 誰が主に判断するか 次へ進める状態 足りないとき
G0 対象 依頼者・開発者 編集先、Git、保存先を特定できる 対象を調べ、不明な部分だけ依頼者へ確認
G1 要件 マネージャー 目的、範囲、受入条件が一致する 読者・利用場面に戻って条件を具体化
G2 実装可能性 技術責任者 既存資産、影響、検証、回復方法を説明できる 調査するか、範囲を小さくする
G3 完了 開発者・必要なレビュー担当 差分と検証証拠が条件に対応する 該当する実装または要件に戻す
G4 共有 指定された公開担当 公開先と公開内容が依頼に一致する 保存先・権限・未確認事項を解消

G0〜G4 は判断の整理用の名称です。既存の依頼で認められた操作を再承認させたり、新しい会議を必須にしたりするものではありません。外部公開や本番反映は、対象・範囲について既存の指示を確認して扱います。

4. 進捗は成果物と未確定事項で見る

進捗共有では「何ができたか」「何がまだ分からないか」「次の確認で何が決まるか」を聞きます。実装行数や AI が動いた時間は、目的を達成した証拠にはなりません。

依存する回答が必要なときは、判断事項と必要な期限を明示します。回答を待たなくてよい調査・資料化・検証は進められます。推測で決めた値は仮定と記録し、完了扱いに紛れ込ませません。

5. 受入と共有を行う

検証・引継ぎ を使い、受入条件と結果を一対一で見ます。実行した確認、実行していない確認、その理由を分けます。GitHub への保存ならリポジトリ、ブランチ、パス、コミットを確認し、リンクから成果物を開きます。

運用後は、新任メンバーが最初の依頼で対象を特定できたか、指示を読み直す回数が減ったか、引継ぎ時の不足が何だったかを確認します。数値の改善は計測できた場合だけ報告し、初回は観測を始めるところからにします。

04 / 開発者Markdown 原本 ↗

開発者の作業フロー

対話型フロー図を開く

1. 作業の境界を固定する

地図の確認コマンド で作業ディレクトリ、Git ルート、remote、ブランチ、基準コミット、既存差分を確認します。AGENTS.md と対象の下位ルールを読み、依頼と照合します。

このワークスペースでは、親フォルダにある開発元と nyonyonyo/ 内の共有コピーが同名の場合があります。編集元と公開先を記録し、同じ内容を両方で独立に変更しないようにします。既存の変更をリセットして作業を始めてはいけません。

2. 現状の入口から変更点まで読む

ファイル名やシンボルを rg / rg --files で探し、入口、呼出先、データ形式、出力、対応するテストの順に読みます。文書に書かれた関係と、コードで確認した関係を区別します。必要なら現象を再現し、変更前の結果を残します。

Observatory なら obs、observatory.py、対象の src/、tests/ が入口です。画面なら viewer/ とビルド生成物の関係も確認します。System Atlas や SAP GUI の作業は、それぞれのフォルダの説明と実行環境へ切り替えます。

3. 要件を実装と検証へつなぐ

要件ID 受入条件 変更する場所・契約 必要な確認
R1 入力に対し期待する結果を返す 関数、CLI、画面、文書の該当箇所 振る舞いを確認するテストや操作
R2 既存利用を壊さない 出力形式、設定、既存版、関連データ 対象を絞った回帰確認や差分比較
R3 指定先から利用できる 保存先、パス、リンク、公開手順 保存後に参照・取得できること

大きな変更では設計・タスクを文書化します。小さな変更ではこの表を依頼や作業記録に埋めるだけで十分です。特定のファイル名を置くだけで自動処理されると想定しません。

4. 既存の解決策を探し、小さく実装する

既存コード、標準機能、導入済み依存で要件を満たせるかを調べます。案が一つに固定されているときは $workspace-detour、利用者の成功条件が曖昧なら $workspace-persona、最初の利用体験を絞るときは $workspace-thriller を選べます。

変更は一つの完了条件に対応する単位へ分けます。分担が依頼や適用ルールで求められている場合は、独立する仕事に担当範囲と完了条件を付けます。複数人・複数エージェントが同じファイルを変更する場合は所有範囲を調整し、他者の編集を戻さないようにします。

5. 変更の種類に合わせて検証する

変更 最初に行う確認 広げる条件
文書・テンプレート 要件との一致、リンク、例、表記、生成 HTML の表示 構成や生成処理を変更した場合は関連ページも見る
スキルの指示 名前・説明・形式、使う条件、出力、短い入力例への適用 指示に矛盾がある、手順が再現しない場合
解析・データ変換 対象関数・既存テスト・必要な失敗ケース 出力契約や共通処理に影響、テスト失敗がある場合
画面 変更した状態の操作、必要な画面幅、生成物 共通部品・操作経路・ビルドに影響する場合
外部サービスや業務操作 接続先、実行内容、返った結果 認められた環境での実動作確認が必要な場合

テストを新設するなら実際の振る舞いを固定します。文書の軽微な変更に、実装と同じ文字列をなぞるだけのテストを追加しません。必要な確認が通った後は、新しい懸念がなければ繰り返さず、引継ぎへ進みます。

検証結果にはコマンド、実行ディレクトリ、基準、結果、未確認事項を残します。「コマンドが定義されている」「実行した」「成功した」を別々に扱います。

6. 差分を確認して共有する

変更対象を明示して確認します。下は本版の追加のように v1/ と入口だけを扱う例です。実際の依頼に合わせてパスを変えます。

git diff -- README.md
git status --short
git add -- v1 README.md
git diff --cached --stat
git diff --cached --check
git diff --cached --name-status

新規ファイルは通常の git diff だけでは見えません。ステージされた一覧と内容を確認してからコミットします。意図しないファイルがあれば対象から外し、元の編集内容は保持します。

公開・アップロードまで依頼されていれば、指定された remote・ブランチへ反映して確認します。レビューが必要なリポジトリではその手順に従います。push が競合した場合は最新の変更を確認し、強制 push で他者の履歴を置き換えません。

図の記録

図の種類は workflow です。検証時の入力と生成物のハッシュ・バイト数は マネージャーの delivery 記録、開発者の delivery 記録 に保存しています。公開用の記録からローカルの絶対パスだけを取り除き、ハッシュと検証結果は保持しています。

収まりを確認した画面サイズは、両図とも 1440×900、1600×1000、1920×1080、2048×1320 です。各サイズで文書の幅・高さが画面内に収まりました。最小・最大サイズで明暗両テーマの画面を確認しています。

目視確認の記録 は、ブラウザで実測した寸法と操作結果を記したものです。自動 visual-check の出力ではありません。画面は作業セッション中に確認し、画像ファイルは同梱していません。全エクスポート形式、プレゼンテーション、すべての Viewer 機能を検証したという意味ではありません。

今回の対象外

  • Observatory・System Atlas のアプリ起動、機能改修、全テストの実行。
  • SAP GUI の実環境での業務操作。
  • スキルの全プロジェクトへのインストール、自動選択精度の評価。
  • 実利用者の理解時間・開発速度・満足度の計測。
  • Git タグ、GitHub Release、Web サイトの新規作成。

図の検証は構成の正しさを確認するもので、チーム運用の効果測定ではありません。形式が通ったスキルも、実案件の条件に合わせて見直します。

編集原本は同梱の Markdown。文書はオフラインで閲覧できます。出典リンクはインターネット上のページを開きます。
