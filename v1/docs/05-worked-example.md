# 実例：既存資料を残してワークスペース版を追加する

このガイド自身の作成を、依頼から共有までの記入例にします。対象は `tamagobolo/nyonyonyo/v1/`、調査開始時の基準は `fc2ee7929bd4838272a292f58ded856b275da8b3` です。実行結果の証跡は [確認記録](../validation.md) にまとめます。

## 依頼を受入条件に変える

課題は、以前の資料が特定製品の導入を前提としており、現在のワークスペースで「どこを読み、どう指示するか」が直接分からないことです。今回の目的は、既存の成果を残しながら、この環境の実務に使える独立した版を作ることです。

| ID | 受入条件 | 対応する成果物 | 確認方法 |
| --- | --- | --- | --- |
| R1 | 旧版の内容とパスを保持する | 追加型の `v1/` と入口へのリンク | 基準コミットとの差分と既存ツリーを比較 |
| R2 | 本版に旧製品への前提・名称を持ち込まない | 全 Markdown、スキル、HTML、図、生成スクリプト | ファイル名と本文の表記検索、手順の内容確認 |
| R3 | 実際のワークスペースに合う | 地図、実コードの読み順、実行場所付きコマンド | AGENTS.md、README、スクリプト、package.json との照合 |
| R4 | 3つの役割が行動できる | 役割別フロー、新任シニアの90分、指示文 | 読み手ごとの目的と完了条件を追う |
| R5 | スキルを利用できる形で渡す | `.agents/skills/workspace-*/SKILL.md` と導入説明 | フロントマター、呼出名、配置説明、入力例への適用 |
| R6 | 指定先から取得できる | GitHub の `v1/` | remote のコミット・ファイル一覧で確認 |

## 3つのスキルを使った判断

以下は本版作成で各 SKILL.md の観点を適用した結果です。ユーザーへのインタビューや定量的な利用テストの結果ではありません。人物像と効果の見込みは設計上の仮定です。

| 観点 | 比較・検討した内容 | 本版で選んだこと |
| --- | --- | --- |
| Persona | マネージャーは成果と範囲、開発者は対象と検証、新任シニアは入口と判断根拠を必要とする | 共有する地図の後に役割別の読み順を用意する |
| Detour | 旧版の上書き、用語だけの置換、独立した新版、全面的な開発基盤作り直しを比較する | 旧版を保持し、既存 HTML 生成と図の構造を活用して新版を追加する |
| Thriller | 読み切ることより、新任シニアが最初の正しい指示を出せることに価値がある | 90分の読み順、実コードの入口、対象・検証付きの指示文を用意する |

Detour の判断理由は、独立版なら差分と保管先が明確で、以前の資料を参照できるためです。単語置換だけでは実行環境やスキルの配置の違いが残り、全面的な基盤変更は今回の目的を超えます。

## 実装する単位

| 単位 | 作業 | 完了の見方 |
| --- | --- | --- |
| T1 | 作業対象、ルール、コードの入口を調査する | 確認基準と根拠を示せる |
| T2 | 役割別フロー、テンプレート、スキルを書き直す | R2〜R5 が本文に対応する |
| T3 | HTML ガイドと2つのフロー図を生成する | 表示、リンク、操作、図の検証が通る |
| T4 | 変更差分と既存資料の保持を確認する | 追加と入口の追記に変更が収まる |
| T5 | GitHub の指定先へ保存して確認する | 公開コミットから成果物を取得できる |

## 指示と結果をつなぐ

「資料を作って終わり」ではなく、`v1/README.md` から役割別の本文へ進めること、HTML の内容が Markdown と一致すること、スキルが別フォルダで自動有効になると誤解させないことまで確認します。

今回は資料とその生成物の追加です。Observatory、System Atlas、SAP GUI の機能改修や本番実行は含めません。そのため、それらの動作を新たに実行確認したとは報告しません。

GitHub での公開後、修正が必要なら本版へ追加コミットを行います。資料の改訂を取り消す場合も、対象の差分を確認してから戻します。既存資料を削除したり、共有ブランチを強制的に巻き戻したりする必要はありません。
