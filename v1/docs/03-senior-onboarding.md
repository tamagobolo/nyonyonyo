# 新任シニアが90分で把握し、的確な指示を出す

目標は、全ファイルを読むことではありません。「どこを変えるか」「何を維持するか」「何で完了を判断するか」を根拠付きで言える状態にすることです。90分は目安で、基盤の動作確認まで保証する時間ではありません。

## 0〜15分：対象とルールを確定する

[ワークスペースの地図](00-workspace-map.md) を読み、[プロジェクト把握](../templates/project-context.md) の対象・基準を埋めます。対象ディレクトリ、Git ルート、remote、ブランチ、基準 SHA、既存差分を確認します。

`nyonyonyo/AGENTS.md`、対象フォルダの指示、README、必要な既存設計資料を読みます。親のワークスペースとリポジトリを同じものとして扱っていないか、配布されたスキル原本を読み込み済みと取り違えていないかを確認します。

この段階の成果は「今回触る範囲と守る条件を2〜3文で言えること」です。

## 15〜40分：一本の処理をソースで追う

共有ツールを理解する場合は、以下の順で追います。ファイルの存在と静的な関係は基準コミットで確認済みです。実行時の挙動は担当する変更に必要な範囲で追加確認します。

| 読む場所 | 確認すること | 指示にどう使うか |
| --- | --- | --- |
| `obs` | Python 実行環境を選び、CLI へ渡す | 起動失敗と解析の不具合を分ける |
| `observatory.py` の parser / main | コマンド分岐、対象と出力先、出力ロック、終了コード | CLI の入力・出力・失敗の契約を特定する |
| `src/scanner.py` の `scan` / `compare` | 解析と差分比較、未完了状態の扱い | データの生成点と互換性を考える |
| `scripts/js-analyze.mjs` | JS / TS の解析経路 | Python 側と別の解析経路を見落とさない |
| `src/reporting.py` の `write_report` | JSON・Markdown・HTML の出力 | 一つの変更が複数の出力へ及ぶか確認する |
| `viewer/main.jsx` と `scripts/build.mjs` | 表示元と `assets/` の生成関係 | ソースと生成物を整合させる必要を判断する |
| `tests/test_observatory.py`、`tests/test_integration.py` | 既存の契約・失敗ケース | 変更に合う確認を選ぶ |

例えば差分比較なら、「不完全な解析結果から削除と断定しない」ことを扱う `test_delta_and_incomplete_never_claims_removal` を読む手がかりにできます。テスト名の存在だけで、今回の差分が合格しているとは判断しません。

実装の入口が違う場合は、この表を対象の入口・中核処理・出力・テストへ置き換えます。System Atlas を調べるのに、Observatory のテストだけで品質を説明しないでください。

## 40〜60分：事実、仮説、未確認事項を分ける

| 区分 | 記入例 |
| --- | --- |
| 確認した事実 | `scripts/build.mjs` は画面資産を生成し、`src/reporting.py` はその資産を HTML に含める |
| 変更に関する仮説 | 表示の追加には、画面ソースと生成物の両方を更新する必要がありそう |
| 次に確認すること | 出力データに必要な値があるか、既存の画面部品で表現できるか |
| 未実行 | 対象の画面操作、ビルド、関連テスト。実行した場合だけ結果を追記する |

重要な設計の選択があるときだけ、[意思決定記録](../templates/decision-record.md) に案・判断理由・残る課題を残します。資料だけで判断できない部分は、担当者への質問か小さな再現で確かめます。

## 60〜80分：最初の指示を作る

```text
対象：tamagobolo/nyonyonyo の v1/。
基準：作業開始時のブランチとコミット、既存差分を記録してください。
目的：新任シニアが、変更対象と検証方法を特定して最初の指示を出せる資料にする。
範囲：docs/03-senior-onboarding.md と関連する指示文。HTML まとめ版も整合させる。
維持条件：既存版と他プロジェクトのファイルは保持する。
根拠：AGENTS.md、実ファイルの入口と責務、既存の構造説明を読む。
完了条件：対象、契約、検証、未確認事項を含む指示例があり、相対リンクが開く。
検証：文書と実ファイルの対応、リンク、生成 HTML の該当章を確認する。
共有：依頼された保存先へ反映し、リンク・コミット・確認結果を報告する。
```

実際のコード変更では「範囲」をファイルまたはモジュールに、「完了条件」を観測できる振る舞いに置き換えます。解法を細かく固定する前に、既存の実装で満たせるかを調べる余地を残します。

## 80〜90分：指示を自己点検する

1. 編集元、Git リポジトリ、公開先を取り違える余地がないか。
2. 根拠のある現在の振る舞いと、期待する変更を区別したか。
3. 互換性や既存版など、維持する条件があるか。
4. 完了を証明する検証と実行場所を説明できるか。
5. 不明点を仮定で埋めず、必要な調査や担当を指定したか。

この5点を満たした指示を最初の小さな変更に使います。引継ぎで判明した不足を資料へ戻すことで、次の参加者の理解を速めます。包括的なアーキテクチャ再設計を初日から始める必要はありません。
