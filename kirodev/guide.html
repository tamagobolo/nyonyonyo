01 / はじめにMarkdown 原本 ↗

Kiro 開発フローガイド

既存プロジェクトへ Kiro を導入し、マネージャー・開発者・新任シニアエンジニアが、同じ要件と検証結果を使って判断するための実務ガイドです。

入口は ブラウザで読むガイド。 編集・レビューの原本はこのフォルダの Markdown です。調査基準日は 2026-09-17。対象は Kiro を使う開発チームであり、Kiro 製品そのものの社内開発プロセスを説明するものではありません。

読む順番

読み手 最初に読む 次に使う
マネージャー マネージャーの作業フロー 変更依頼テンプレート
開発者 開発者の作業フロー 指示文集
初参加のシニアエンジニア 90分の導入手順 プロジェクト把握シート
導入責任者 Kiro の機能と役割 導入・保守の手順

共通の進め方

課題と成功条件 → コードの現状確認 → 要件 → 設計候補の比較 → 設計とタスクの確定 → 小さな実装 → 検証・レビュー → 受入・公開・効果確認。

人格スキルは「設計候補の比較」に使います。発散した案をそのまま実装せず、採用した考えを要件・設計へ反映します。事業上の受入判断、技術判断、Kiro の操作権限は別々に扱います。

成果物 用途

一連の記入例 既存 SaaS の CSV 出力改善を例に、要件から検証まで追う
3つのスキルの設計と適用記録 Persona・Detour・Thriller を今回のフローへどう適用したか

出典と確認範囲 公式仕様、独自の運用提案、未検証部分の区別

本書の前提

ユーザー指定により 既存プロジェクトへの導入を対象とします。開発者は IDE 中心、マネージャーは文書・PR と必要に応じた Kiro Web を利用する想定です。GitHub がない場合もローカル IDE で同じ成果物を作成できます。

対象プロジェクトのソースコード、組織の承認規程、CI、デプロイ環境は未提供です。そのため、本書の役割分担・判断点・ファイル命名・時間配分は提案であり、導入先の現行手順に合わせて決めます。サンプルの数値・パス・担当名を実在のものとして扱わないでください。

「Detour・Persona・Thriller」は Cocoda の事例記事 に着想を得ています。原本の GitHub 配布先は確認できていないため、同梱スキルは 独自再構成です。特に Thriller の具体的な評価手順は本書で定義したもので、記事の原実装を再現したという主張はしません。

すぐ使う

  1. この kirodev フォルダを Kiro IDE で開き、本書を読みます。
  2. 実プロジェクトでは既存の .kiro/ を確認し、同梱の3つのスキルフォルダだけを .kiro/skills/ にコピーまたはローカルインポートします。導入手順に従って認識を確認します。
  3. 把握シートを対象コードの証拠で埋めます。
  4. 低リスクの変更1件で 指示文集を試し、要件IDとテストを対応させます。

図の本文は日本語です。Archify の操作 UI と HTML の言語属性は製品の対応言語に従い英語です。文書閲覧用 guide.html の言語は日本語です。

02 / Kiro の機能と役割Markdown 原本 ↗

Kiro の機能とチームでの役割

入口に戻る · 公式情報の確認日と出典

最初に押さえること

Kiro は、要件・設計・タスクを作成し、コード変更と検証を支援する開発エージェントです。本書では「何を任せたか」「何を根拠に完了とするか」をファイルと PR に残し、別の担当者が引き継げるように運用します。対象コードの説明は、チャットでの推測ではなく、実ファイル・実行結果と照合します。

使い分け

機能 Kiro の公式上の役割 本書での使い方
Specs 変更ごとの要件・設計・タスクを構造化 変更の契約。何を作るか、どこまで完了したかを共有
Steering プロジェクトの方針・技術・構造を継続的に伝える 複数の変更に共通する、確認済みの前提
Agent Skills 必要なときに読み込む再利用可能な手順 今回の3つの設計思考を呼び分ける
Hooks イベントに応じてコマンドやプロンプトを実行 チームで確認済みの反復チェックを補助
MCP 外部ツールやデータへの接続 必要なサービスだけ接続。権限は個別に管理
Permissions エージェントが操作できる範囲を制御 作業に必要な操作範囲と、組織の権限を合わせる

出典：Specs・Steering・Skills・Hooks・Permissions。MCP は公式ドキュメントの機能項目として掲載されています。公式 Docs

Steering に一度限りの作業計画をためず、Specs に置きます。Skills に会社の全規程を複製せず、必要な前提ファイルを入力として指定します。技術スタックやディレクトリ構造を変えたら、実装と Steering を同じ変更で更新する運用を推奨します。

利用する画面

利用面 この導入での担当 本書の扱い
Kiro IDE 開発者、技術責任者 ローカルのコード・差分・テストを見ながら進める標準
Kiro Web マネージャー、委任する開発者 接続済みリポジトリを指定して調査や作業を依頼する選択肢
Kiro CLI ターミナル中心の開発者 既存の CLI 運用がある場合に採用。コマンドは導入版のヘルプで確認

Kiro Web の通常セッションは対話型で、New session → Select repo → 依頼入力から開始できます。PR を作成するよう依頼する操作は外部のリポジトリを変更します。Web の操作

GitHub 連携ではアプリ側の対象リポジトリ設定と利用者自身の権限が必要です。作業の委任には書き込み権限が必要とされています。マネージャーにその権限がない場合は、変更依頼を作成して開発者へ渡す運用で構いません。同じ Issue を複数人が委任すると別タスクになり得るため、委任担当者を1名に決めます。GitHub 連携

Spec の選び方

状況 入口 このチーム運用での確認点
利用者の困りごとから機能を改善 Feature / Requirements-First 要件と対象外を先に決め、既存の制約を設計へ反映
API移行・基盤制約など技術上の起点が明確 Feature / Design-First 設計から導いた要件が業務目的を満たすか確認
原因調査が必要な不具合 Bugfix Spec 現在・期待・変えてはいけない振る舞いを分ける
十分理解された小さな変更 Quick Spec 一括生成された文書を、実装前に必要な範囲でレビュー
純粋な質問・小さな調査 通常のチャット 根拠・未確認事項を残す。全件に大きな Spec を要求しない

Requirements-First は要件→設計→タスク、Design-First は設計→要件→タスクです。Quick Spec には各文書間の承認ステップがありません。新任者の初回変更は、途中で前提を照合しやすい通常の Feature Spec を推奨します。Feature Specs・Quick Spec・Bugfix Specs

成果物の置き場所

公式の基本構造は .kiro/specs/ 配下の requirements.md（バグなら bugfix.md）、design.md、tasks.md です。Steering の基本ファイルは .kiro/steering/product.md・tech.md・structure.md、Skills は .kiro/skills/<name>/SKILL.md です。Specs・Steering・Skills

本書では次の追加ファイルをチーム独自の記録として提案します。Kiro が自動生成する前提にはしません。

docs/project-context.md                # 実コードに基づく把握シート
docs/changes/<change-id>/brief.md       # 目的・対象外・成功条件
docs/changes/<change-id>/options.md     # 発散した案・採否・根拠
docs/changes/<change-id>/decision.md    # 判断者・対象リビジョン・理由
docs/changes/<change-id>/verification.md # 検証コマンド・結果・残課題
.kiro/specs/<feature>/                 # Kiro の Spec 一式

権限とレビューを混同しない

「要件を承認した」は、設計された機能に合意したという記録です。「ターミナル操作を許可した」は、ツールに操作権限を与えたという意味です。「PR を承認した」は、リポジトリでのレビュー判断です。本書の G0〜G4 は業務上の判断点で、Kiro の設定項目や組み込みのロールではありません。

Steering に禁止事項を書くことと、操作権限で強制することも別です。権限・保護ブランチ・必須 CI は導入先で確認します。調査プロンプトだけで書き込みが技術的に禁止されるとは扱いません。Permissions

03 / マネージャーMarkdown 原本 ↗

マネージャー用の作業フロー

入口 · フロー図を開く

この役割の到達点

「誰のどの問題を、どこまで解くか」と「何を見れば成功と言えるか」を決め、開発者が実装へ進める依頼にします。技術責任者は設計の妥当性、開発者は実装と検証の証拠を担当します。小規模チームでは兼任できますが、記録上の判断は分けます。

以下は本書が提案する運用です。既存の決裁・PR・公開規程がある場合は、その担当名と判断点へ対応させます。

1件の変更を進める

工程 マネージャーの作業 Kiro への依頼・他職種の作業 出力・次へ進む条件
1. 依頼を受ける 問題、対象者、観測した困りごと、優先理由を記入 現行動作・既存機能・関連 Issue の調査を依頼 brief.md。事実と要望を分ける
2. 利用者視点を比較 /team-persona で利用者・運用者・承認者の成功条件を比較 技術責任者がコードで制約を確認 options.md。視点の衝突が見える
3. 解き方を広げる 行き詰まる場合 /team-detour、体験の磨き込みなら /team-thriller 通常案・代替案・費用・影響・検証方法を同じ軸で比較 採用案と不採用理由。全スキルを毎回実行する必要はない
4. 範囲を決める 必須・後回し・対象外、受入条件、成功指標を決定 Requirements-First の Spec へ採用案を反映 G1：要件合意。曖昧な条件をテスト可能にする
5. 実装に引き継ぐ 期限と事業上の制約を説明 技術責任者が設計・移行・回復方法・タスク依存を確認 G2：設計と実装範囲の合意。依頼先・判断者が明確
6. 進捗を確認 遅延要因と必要な意思決定に対応 完了した受入条件、証拠、未解決の依存を報告させる タスク数だけで進捗を評価しない
7. 受け入れる シナリオを試し、利用者の目的が満たされるか判断 開発者が要件→テスト→結果の対応、PR、残課題を提示 G3：技術レビュー。G4：事業受入と公開判断
8. 効果を測る 指標と問い合わせの変化を確認 公開担当が段階反映・監視・障害時の回復を担当 結果を次の依頼へ反映

判断点と責任者

判断点 判断の対象 主に判断する人 不合格なら
G0 現状把握 基準ブランチ、既存動作、検証手順の信頼性 技術責任者 証拠を取り直す。要件の検討自体は続けられる
G1 要件合意 解く問題・受入条件・対象外 マネージャー / 業務責任者 依頼者へ質問し、要件を修正
G2 設計合意 契約、影響範囲、移行、テスト、依存 技術責任者 設計へ戻す。範囲変更なら G1 も更新
G3 技術レビュー 実装差分、CI、回帰、運用上の可否 リポジトリのレビュアー 指摘を該当タスクへ戻す
G4 受入・公開 受入条件と公開条件、残リスク 業務責任者と公開責任者 未達要件を直すか、対象外へ変える判断を記録

G1〜G4 を毎回会議にする必要はありません。既存の Issue コメント、PR レビュー、リリース記録で満たせます。判断した文書の版やコミットを必ず識別し、後で変更された要件まで承認したと扱わないようにします。

そのまま使える最初の指示

既存プロジェクトの改善依頼を整理してください。今回は要件案の作成までです。
対象：〈リポジトリ・対象ブランチ・対象機能〉
困りごと：〈観測した事実、問い合わせや操作の具体例〉
対象者：〈主利用者・運用担当〉
成功条件：〈誰が何をできればよいか〉
固定する制約：〈既存API、納期、互換性、運用条件〉
対象外：〈今回扱わないこと〉
参照：〈brief、project-context、関連Issueのパス〉

/team-persona を使って、利用者・運用者の成功条件と衝突を整理してください。
必要な事実をリポジトリで確認し、根拠パスと未確認事項を分けてください。
通常案と改善案を比較し、受入条件案を requirements.md 向けにまとめてください。
コード実装やPR作成は、この依頼の範囲に含めません。

これは Kiro の組み込みコマンドの一覧ではなく、同梱スキル導入後に使う依頼文です。単独で呼ぶ場合は /team-persona をチャット入力で選択します。Skills の呼出仕様

進捗会話の型

「何％できたか」だけを聞かず、次の4点を1行ずつ報告してもらいます。

  • 達成済み：受入条件ID、PR・テスト等の証拠。
  • 現在の詰まり：再現条件、外部依存、情報不足の種類。
  • 必要な判断：選択肢、推奨案、放置した場合の影響、回答期限。
  • 次の作業：担当者、タスクID、完了と判断する証拠。

例：「R-1/R-2 は検証済み。R-3 は上限件数が未決定。5千件と1万件の実測を添付し、業務責任者に本日中の判断を依頼。決まり次第 T-3 の境界値テストへ進む」。数値は説明例です。

途中で要望が増えた場合

  1. 追加要望が、現在の受入条件の不足か、新しい目的かを区別します。
  2. Kiro に影響する要件・設計・タスク・テストのIDを列挙させます。
  3. 納期・コスト・公開範囲を比較し、採用・延期・分割を決めます。
  4. decision.md と該当文書を更新してから、影響を受ける実装を再開します。影響のない作業まで止める必要はありません。

Web を使う場合

接続済みの対象リポジトリを選び、調査・文書化・実装のどこまでを委任するか明記します。ローカルにしかない変更はクラウド側の前提に含めず、対象ブランチ・基準 SHA と成果物を渡してください。本書では IDE と Web 間のチャットが自動で完全に引き継がれるとは想定しません。Web の操作・GitHub 連携

開発者用の作業フロー

入口 · フロー図を開く · 指示文集

開始前にそろえるもの

対象リポジトリ・ブランチ・基準 SHA、変更目的、受入条件、変更可能な範囲、実行環境、レビュー担当者を確認します。引継ぎが口頭だけなら 変更依頼へ要点を残します。未コミット変更がある場合は所有者と作業範囲を把握します。

1. 現状を確かめる

README、既存の AGENTS.md / Steering、依存定義とロックファイル、起動入口、主要ユースケース、データ境界、CI を読みます。実ファイルを根拠に 把握シートを作り、既存テストを1つ実行して、変更前の状態を記録します。

git status --short
git branch --show-current
git rev-parse HEAD
rg --files -g '!node_modules' -g '!vendor' -g '!dist'

この4コマンドは調査の入口です。依存インストールやテストのコマンドは、対象リポジトリの README・CI・パッケージ定義で確認してから使います。npm test や特定のフレームワークを前提にしません。

G0 の目安は「主要な1要求の入口→処理→データ→外部依存を説明でき、代表テストの成功/失敗と理由を示せること」です。既知の失敗がある場合は新しい回帰と区別し、対象変更に関係する検証が可能か技術責任者と判断します。

2. Spec を作成・更新する

IDE では Specs の + またはチャットの Spec から、Feature / Bug を選びます。機能改善は通常 Requirements-First、技術設計から始まる場合は Design-First を使います。画面ラベルが異なる版では公式の対象版の案内を確認してください。Specs の開始操作

要件には以下を含めます。

  • 主な成功シナリオと、条件付きの振る舞い。
  • 権限不足、入力不正、タイムアウト、同時更新など、その変更で意味のある異常系。
  • 維持する API・データ・UI の契約、対象外。
  • 観測可能な受入条件と要件ID（本書では R-1 等を使用）。

「速い」「直感的」をそのまま受入条件にせず、対象操作・入力条件・測定方法を決めます。仕様が未確定の項目は推測で埋めず、質問と担当者を付けます。G1 で採用する要件の版を決めます。

3. 必要な設計候補を発散・比較する

共通入力は要件、現状の実装根拠、固定する制約、今回の対象範囲です。

スキル 開発時の用途 必ず戻す制約
/team-persona 主利用者・低権限利用者・運用者の視点で見落としを探す 同じ業務ルールとアクセス制御
/team-detour 構造の異なる解き方を比較する。設定・運用改善も候補にする 互換性、データ保護、可用性、依頼範囲
/team-thriller 失敗復帰・完了確認など最重要体験を具体化する 実在の機能とデータ、性能とアクセシビリティ

options.md に「通常案 / 候補 / 利用者への効果 / 変更箇所 / コスト / 未確認 / 採否」を残します。候補ごとにコードを作る必要はありません。UI がない内部処理なら Persona は呼出元・運用者の視点に置き換えられます。確定した不具合の最小修正では発散工程を省略できます。

4. 設計・タスクを確定する

design.md に変更対象、公開インターフェース、入力と出力、状態遷移、失敗時の挙動、移行、テスト方針を記載します。既存の実装を再利用する箇所と理由を示し、必要なら短い意思決定記録を残します。非互換変更やデータ移行は、前進手順だけでなく回復可能性も確認します。

tasks.md では各タスクを、担当可能な範囲・依存タスク・対応要件・完了条件まで具体化します。G2 では技術責任者が設計と実装範囲を確認します。

T-1: CSV出力サービスの認可・条件・上限を確認し、不足を修正する
対応要件: R-1 / R-2 / R-3
依存: T-0で現行仕様と契約を調査
変更範囲: 実在確認済みの対象モジュールと関連テスト
完了条件: 権限・条件・上限内・上限超過を検証し、既存出力との互換を確認
引継ぎ: 実行コマンド、終了状態、結果パス、残課題

Kiro はタスクの依存関係に基づく並列実行をサポートします。本書では初回は1タスクで前提を確認し、独立性が確認できたものだけをまとめて実行する運用を推奨します。共通のスキーマ、ロックファイル、同一関数を同時変更する作業は調整が必要です。タスク実行

5. 小さく実装・検証する

  1. 対象タスクと参照 Spec の版を指定します。
  2. 意図した振る舞いを最小の変更で実装します。
  3. 変更に対応するテストを実行し、既存動作が保たれるか確認します。
  4. 型・静的解析・結合テスト・ビルドは既存 CI と変更範囲に合わせて実行します。
  5. 差分を読み、要件外の変更、意図しない生成物、依存追加がないか確認します。
  6. 要件→タスク→テスト→結果を対応させ、未実行は理由を記録します。

テスト生成数や Kiro の「完了しました」という文章は、検証の代わりになりません。失敗した検証は再現条件を絞って修正し、意味のある成功結果が得られてから完了状態にします。UI の変更では操作・表示・キーボード・空状態や異常状態など、要件に関係する範囲を目視でも確認します。

6. PR と受入の引継ぎ

PR には具体的な変更前後、関連 Spec、要件ID、テスト結果、移行・ロールバック、既知の制約を添えます。G3 の技術レビュー後、業務責任者へシナリオと検証結果を渡し、G4 の受入・公開判断につなげます。検証と引継ぎテンプレートを使えます。

公開は既存の CI/CD と責任者の手順で行います。本書の導入だけでデプロイ権限や手順を変更することは想定しません。反映後の代表シナリオと監視指標を確認し、不達なら事前に決めた回復手順へ移ります。ロールバック不能な移行は、前進修正の方法と担当者を公開前に決めます。

不具合の場合の分岐

Bugfix Spec では bugfix.md に 現在の不正な動作 / 正しい期待動作 / 維持する既存動作を記録します。再現条件→原因仮説→証拠→修正→再現テストの成功→回帰確認の順で進めます。原因が確定している小さな修正に、3つの人格による発散を機械的に追加しません。Bugfix Specs

  2. 対象：リポジトリ、ブランチ、基準 SHA、Spec とタスクID。
  3. 根拠：実ファイル、既存の類似実装、決定済みの設計。
  4. 範囲：変更してよいモジュールと今回は触れない契約。
  5. 条件：成功・失敗・境界値・互換性の受入条件。
  6. 裁量：実装者が決められる部分と相談が必要な変更。
  7. 検証：実在するコマンド、期待結果、必要な証拠。
  8. 引継ぎ：成果物の場所、レビュー担当、残課題の伝え方。

不足した項目をすべて事前質問で埋める必要はありません。コードから確かめられることは調査し、事業上の判断だけを責任者へ質問します。

初回レビューで自分が見るところ

  • 要件にない振る舞いが、人格スキルの提案から混入していないか。
  • 既存設計と矛盾する変更を、根拠なしに「ベストプラクティス」で正当化していないか。
  • テストが実装の写しにならず、利用者が必要とする結果を確かめているか。
  • 更新対象のドキュメントとコードが同じ版になっているか。
  • コードを戻せば十分か、データや外部副作用の回復も必要か。

導入完了の判定

自分の言葉で代表ユースケースを説明し、任意の受入条件から対応コードとテストへたどれれば、実装指示を出す基礎ができています。把握シートの未確認事項を見ずに断定してしまう場合は、調査の範囲をもう一段狭めて確かめます。
