# 既存プロジェクトへの導入と保守

[入口](../README.md) · [スキルの意図](06-skill-design.md)

## 今回作成したものと、導入先で行うこと

このフォルダには文書、テンプレート、3つのスキル、2つの図を用意しています。実プロジェクトのコード変更、Kiro のインストール、GitHub 連携、Hooks・権限設定、PR・本番公開は実行していません。

既存チームの手順を置き換える前に、小さな変更1件で使い、役割名・判断点・検証コマンドを合わせます。

## スキルを使えるようにする

Kiro はプロジェクトの `.kiro/skills/<name>/SKILL.md` を認識します。IDE の Agent Steering & Skills から `+` → Import a skill → Local folder でも取り込めます。[公式 Skills](https://kiro.dev/docs/skills/)

1. 対象プロジェクトの既存 `.kiro/skills/` に同じ名前がないか確認します。
2. このガイドの `.kiro/skills/` にある `team-persona`、`team-detour`、`team-thriller` の3フォルダを対象側へコピーします。同名があれば中身を比較し、必要な差分を統合します。
3. Kiro で対象プロジェクトを開き直すか、新しいセッションで認識を確認します。
4. チャットで `/` を入力し、対象スキルが候補に現れることを確認します。
5. 実データを使わない小さな設計課題で1つずつ呼び、入力不足・固定制約・出力が想定通りか確かめます。

Kiro Web から使う場合、ワークスペーススキルを対象リポジトリで利用できる状態にします。ローカルの未コミットファイルや `~/.kiro/skills/` が自動でクラウドに存在するとは想定しません。組織の通常のレビューと反映手順で共有してください。[Skills の対象範囲](https://kiro.dev/docs/skills/)

見つからない場合は、フォルダ名と frontmatter の `name`、配置するルート、ファイル名の大文字小文字、対象バージョンを確認します。カスタムエージェントを使用している場合は、Steering と Skills の読み込み設定も確認します。公式ではカスタムエージェントの `resources` で参照を指定する例が示されています。[Steering](https://kiro.dev/docs/steering/)・[Skills](https://kiro.dev/docs/skills/)

## プロジェクトの前提を整える

まず [把握シート](../templates/project-context.md)を埋め、確認済みの内容を `.kiro/steering/` へ整理します。Kiro IDE には基礎の Steering を生成する UI がありますが、生成結果の事実確認は必要です。[公式 Steering](https://kiro.dev/docs/steering/)

| ファイル | 入れる情報 | 根拠 |
|---|---|---|
| `product.md` | 目的、利用者、主要機能、業務上の制約 | 既存の業務仕様、責任者が確認した brief |
| `tech.md` | 現在の言語、依存、実行環境、検証コマンド | 依存定義、ロックファイル、CI |
| `structure.md` | 実際のモジュール責任、入口、依存方向 | 実コード、追跡したユースケース |

常時読み込む情報は短く保ち、個別変更の履歴は Spec や決定記録へ置きます。`always`・`fileMatch`・`manual` などの取り込み方法は、導入版の公式仕様と照合して選びます。今回の配布物には未記入の Steering を有効状態で置いていません。

## 初回導入の順序

| 段階 | 実施内容 | 終了条件 |
|---|---|---|
| 準備 | 対象・担当者・利用面・既存ルールを把握 | 把握シートの重要な未確認に担当が付く |
| 試行 | 低リスクの変更1件を Spec から受入まで通す | 要件とコードとテストを対応できる |
| 振り返り | 指示の不足、手戻り、記録負担を確認 | 続ける項目と削る項目を決める |
| 共有 | スキルと短い Steering を通常のレビューで共有 | 新しい参加者が同じ入口へ到達できる |
| 拡張 | 必要なら Web、MCP、Hooks を追加 | 手作業で有効と確認済みの反復処理から自動化 |

## Hooks は最後に小さく追加する

Hooks はイベントに応じてコマンドやプロンプトを実行する機能です。トリガーごとに IDE・CLI・Web の対応が異なり、公式ページには概要表と詳細表の粒度差もあります。`PostFileSave` など特定のトリガーが全利用面で同じ動作をするとは断定せず、使うトリガー・版・利用面を確認してください。[公式 Hooks](https://kiro.dev/docs/hooks/)

本書では自動実行設定を配布せず、以下の導入基準を提案します。

- まず既存 CI のコマンドを手動で再現する。
- フックの入力、対象ファイル、終了状態、タイムアウトを確認する。
- 自動修正が必要か、検査だけで足りるかを決める。
- 失敗時に作業が止まるか、通知だけかを明示する。
- 実行回数、所要時間、再帰的な再実行の有無を小さな変更で確認する。

Hooks による補助と、サーバー側の必須 CI・保護ブランチによる制御は区別します。

## 文書を古くしない

| 変化 | 更新するもの | 確認する人 |
|---|---|---|
| API・データ・構造が変わる | 対象 Spec、把握シート、関連 Steering | 技術責任者 |
| 業務の受入条件が変わる | brief、requirements、decision | 業務責任者 |
| CI・起動・公開手順が変わる | tech、verification のひな形、公開手順 | 開発・運用担当 |
| Kiro を更新する | 利用面、操作名、スキルの呼出、Hooks互換性 | 導入担当 |
| スキルが誤った場面で発動する | description と具体的な判断条件 | スキル担当 |

Kiro の公式仕様は本書の [出典一覧](../sources.md)から再確認します。モデル名、料金、クォータは変化が早く、本書の作業フローの固定条件に含めていません。

## 導入の効果を見る

初回の比較値を残し、最初の数件で「レビュー差し戻しの原因」「要件変更による手戻り」「新任者が最初の指示を出すまでの時間」「公開後の回帰」を見ます。数値目標は現状を測ってから決めます。生成コード量や AI のタスク消化数だけを成果指標にしません。
