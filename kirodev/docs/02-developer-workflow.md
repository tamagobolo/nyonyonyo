# 開発者用の作業フロー

[入口](../README.md) · [フロー図を開く](../diagrams/developer-workflow.html) · [指示文集](04-instruction-playbook.md)

## 開始前にそろえるもの

対象リポジトリ・ブランチ・基準 SHA、変更目的、受入条件、変更可能な範囲、実行環境、レビュー担当者を確認します。引継ぎが口頭だけなら [変更依頼](../templates/change-brief.md)へ要点を残します。未コミット変更がある場合は所有者と作業範囲を把握します。

## 1. 現状を確かめる

README、既存の AGENTS.md / Steering、依存定義とロックファイル、起動入口、主要ユースケース、データ境界、CI を読みます。実ファイルを根拠に [把握シート](../templates/project-context.md)を作り、既存テストを1つ実行して、変更前の状態を記録します。

```sh
git status --short
git branch --show-current
git rev-parse HEAD
rg --files -g '!node_modules' -g '!vendor' -g '!dist'
```

この4コマンドは調査の入口です。依存インストールやテストのコマンドは、対象リポジトリの README・CI・パッケージ定義で確認してから使います。`npm test` や特定のフレームワークを前提にしません。

G0 の目安は「主要な1要求の入口→処理→データ→外部依存を説明でき、代表テストの成功/失敗と理由を示せること」です。既知の失敗がある場合は新しい回帰と区別し、対象変更に関係する検証が可能か技術責任者と判断します。

## 2. Spec を作成・更新する

IDE では Specs の `+` またはチャットの Spec から、Feature / Bug を選びます。機能改善は通常 Requirements-First、技術設計から始まる場合は Design-First を使います。画面ラベルが異なる版では公式の対象版の案内を確認してください。[Specs の開始操作](https://kiro.dev/docs/specs/)

要件には以下を含めます。

- 主な成功シナリオと、条件付きの振る舞い。
- 権限不足、入力不正、タイムアウト、同時更新など、その変更で意味のある異常系。
- 維持する API・データ・UI の契約、対象外。
- 観測可能な受入条件と要件ID（本書では `R-1` 等を使用）。

「速い」「直感的」をそのまま受入条件にせず、対象操作・入力条件・測定方法を決めます。仕様が未確定の項目は推測で埋めず、質問と担当者を付けます。G1 で採用する要件の版を決めます。

## 3. 必要な設計候補を発散・比較する

共通入力は要件、現状の実装根拠、固定する制約、今回の対象範囲です。

| スキル | 開発時の用途 | 必ず戻す制約 |
|---|---|---|
| `/team-persona` | 主利用者・低権限利用者・運用者の視点で見落としを探す | 同じ業務ルールとアクセス制御 |
| `/team-detour` | 構造の異なる解き方を比較する。設定・運用改善も候補にする | 互換性、データ保護、可用性、依頼範囲 |
| `/team-thriller` | 失敗復帰・完了確認など最重要体験を具体化する | 実在の機能とデータ、性能とアクセシビリティ |

`options.md` に「通常案 / 候補 / 利用者への効果 / 変更箇所 / コスト / 未確認 / 採否」を残します。候補ごとにコードを作る必要はありません。UI がない内部処理なら Persona は呼出元・運用者の視点に置き換えられます。確定した不具合の最小修正では発散工程を省略できます。

## 4. 設計・タスクを確定する

`design.md` に変更対象、公開インターフェース、入力と出力、状態遷移、失敗時の挙動、移行、テスト方針を記載します。既存の実装を再利用する箇所と理由を示し、必要なら短い意思決定記録を残します。非互換変更やデータ移行は、前進手順だけでなく回復可能性も確認します。

`tasks.md` では各タスクを、担当可能な範囲・依存タスク・対応要件・完了条件まで具体化します。G2 では技術責任者が設計と実装範囲を確認します。

```text
T-1: CSV出力サービスの認可・条件・上限を確認し、不足を修正する
対応要件: R-1 / R-2 / R-3
依存: T-0で現行仕様と契約を調査
変更範囲: 実在確認済みの対象モジュールと関連テスト
完了条件: 権限・条件・上限内・上限超過を検証し、既存出力との互換を確認
引継ぎ: 実行コマンド、終了状態、結果パス、残課題
```

Kiro はタスクの依存関係に基づく並列実行をサポートします。本書では初回は1タスクで前提を確認し、独立性が確認できたものだけをまとめて実行する運用を推奨します。共通のスキーマ、ロックファイル、同一関数を同時変更する作業は調整が必要です。[タスク実行](https://kiro.dev/docs/specs/)

## 5. 小さく実装・検証する

1. 対象タスクと参照 Spec の版を指定します。
2. 意図した振る舞いを最小の変更で実装します。
3. 変更に対応するテストを実行し、既存動作が保たれるか確認します。
4. 型・静的解析・結合テスト・ビルドは既存 CI と変更範囲に合わせて実行します。
5. 差分を読み、要件外の変更、意図しない生成物、依存追加がないか確認します。
6. 要件→タスク→テスト→結果を対応させ、未実行は理由を記録します。

テスト生成数や Kiro の「完了しました」という文章は、検証の代わりになりません。失敗した検証は再現条件を絞って修正し、意味のある成功結果が得られてから完了状態にします。UI の変更では操作・表示・キーボード・空状態や異常状態など、要件に関係する範囲を目視でも確認します。

## 6. PR と受入の引継ぎ

PR には具体的な変更前後、関連 Spec、要件ID、テスト結果、移行・ロールバック、既知の制約を添えます。G3 の技術レビュー後、業務責任者へシナリオと検証結果を渡し、G4 の受入・公開判断につなげます。[検証と引継ぎテンプレート](../templates/verification-handoff.md)を使えます。

公開は既存の CI/CD と責任者の手順で行います。本書の導入だけでデプロイ権限や手順を変更することは想定しません。反映後の代表シナリオと監視指標を確認し、不達なら事前に決めた回復手順へ移ります。ロールバック不能な移行は、前進修正の方法と担当者を公開前に決めます。

## 不具合の場合の分岐

Bugfix Spec では `bugfix.md` に **現在の不正な動作 / 正しい期待動作 / 維持する既存動作**を記録します。再現条件→原因仮説→証拠→修正→再現テストの成功→回帰確認の順で進めます。原因が確定している小さな修正に、3つの人格による発散を機械的に追加しません。[Bugfix Specs](https://kiro.dev/docs/specs/bugfix-specs/)

## 途中で止まったとき

| 状況 | 次にすること | 戻り先 |
|---|---|---|
| 要件と実コードが食い違う | 差異、根拠パス、影響する受入条件を提示 | G0 / G1 |
| Spec と実装がずれた | どちらを変えるか判断し、同じ変更で更新 | G1 / G2 |
| テストを実行できない | 実行条件・環境不足を記録し、成功と扱わない | 環境担当 / G3 |
| UI案が似通う | Detour で変える前提を1つ明示し、構造を比較 | 候補比較 |
| 仕様変更で作業が膨らむ | 影響するタスクと新旧の範囲を列挙 | G1 |
| 公開後の指標が悪化 | 回復条件に従い停止・切戻し・前進修正 | 公開責任者 |
