# Kiro への指示文集

[入口](../README.md) · [記入済みの例](05-worked-example.md)

`〈…〉` を実際の情報へ置き換えて使います。ここに書かれた `/team-*` は同梱の再構成スキル名です。役割・G番号・R/T番号は本書の運用上の識別子であり、Kiro の組み込みコマンドではありません。

## 共通ヘッダー

```text
目的：〈利用者の困りごとと期待する変化〉
対象：〈リポジトリ / ブランチ / 基準SHA〉
参照：〈project-context、Spec、関連コードの実在パス〉
今回の作業段階：〈調査 / 要件 / 設計 / 実装 / レビュー〉
対象範囲：〈変更してよい機能・モジュール〉
維持する契約：〈API、データ、権限、既存UIなど〉
受入条件：〈R-IDごとの確認可能な振る舞い〉
成果物：〈文書パス / タスクID / 差分 / 検証結果〉
判断が必要になる条件：〈範囲拡大、互換性変更など具体的な境界〉
```

## A. 現状の調査

```text
共通ヘッダーの対象を調査し、docs/project-context.md を作成してください。
入口、主要ユースケース、依存、データ境界、CI、既知の不具合を整理してください。
各説明に根拠のファイルパスとシンボルを付けてください。
READMEと実装が違う場合は両者を併記してください。
確認済み / 推定 / 未確認を区別し、重要な未確認には次の調査方法を付けてください。
```

## B. マネージャーの要件整理

```text
brief.md と現状把握をもとに Feature Spec の要件案を作成してください。
成功・異常・維持する動作を、条件と期待結果の形で記述してください。
各要件にIDを付け、対象外と未決定事項も分けてください。
今回は requirements.md の作成とレビュー用の質問までです。
```

## C. Persona の実行

```text
/team-persona
対象：〈機能〉
参照：〈要件、現状、固定制約のファイル〉
視点：主利用者、権限の低い利用者、運用担当。
全視点に同じ確定要件を渡し、それぞれの成功条件と困りやすい状態を比較してください。
現行案に欠ける情報、操作、復帰経路を列挙し、要件追加候補として提案してください。
```

## D. Detour の実行

```text
/team-detour
対象：〈行き詰まっている問題〉
通常案：〈現行の解決策〉
固定する制約：〈互換性・権限・整合性・依頼範囲〉
動かせる前提：〈画面構造 / タイミング / 作業の順序など〉
前提を変えた候補を比較し、最後に固定制約へ戻して実現できる工夫を抽出してください。
非採用案の理由も options.md に残してください。
```

## E. Thriller の実行

```text
/team-thriller
対象：〈機能〉
最重要の瞬間：〈利用者が成功・失敗を理解して次へ進む場面〉
変えたい観測結果：〈迷い、やり直し、完了確認の負担など〉
既存要件と実在機能の範囲で、その瞬間を改善する小さな案を比較してください。
見栄えだけの差を避け、効果の確認方法と実装費用を示してください。
```

## F. 設計とタスクへの収束

```text
options.md で採用した案だけを、確定要件に対応づけて design.md に反映してください。
既存コードの再利用、変更する契約、データ・状態の変化、異常時の処理を記述してください。
移行と回復が必要ならその方法、テストの観点、未確認事項を含めてください。
tasks.md は、依存、対応要件、変更範囲、完了条件が分かる単位へ分割してください。
既存の要件から範囲が広がる部分は変更提案として明示してください。
```

## G. 1タスクの実装

```text
〈Specのパス・版〉の〈タスクID〉を実装してください。
要件〈R-ID〉、設計〈該当節〉、既存の類似実装〈パス〉に従ってください。
実装上の局所的な選択は任せます。
公開APIの変更、依存追加、データ移行が必要になった場合は、根拠と代替案を提示してください。
実在する検証コマンド〈確認済みのコマンド〉を実行してください。
結果は、変更ファイル、要件対応、コマンドと結果、未実行項目、残課題で報告してください。
今回の範囲はローカル実装と検証までです。
```

最後の一文は実際の委任範囲に合わせます。PR 作成まで依頼する場合は、対象リポジトリ・ブランチ・PR 作成の意図を明記してください。既に与えた権限を形式的に再確認するためのテンプレートではありません。

## H. シニアのレビュー

```text
〈基準SHA〉から〈変更SHA〉の差分をレビューしてください。
参照は確定要件、design.md、verification.md です。
優先する観点：要件未達、既存契約の破壊、異常系、データ整合性、回復可能性。
指摘には発生条件、実際の影響、ファイル位置、修正の方向を含めてください。
要件からテストへたどれないものを列挙し、未実行を成功扱いしないでください。
今回はレビュー結果の提示までです。
```

## I. 仕様変更・再開時の引継ぎ

```text
基準：〈リポジトリ、ブランチ、最新SHA〉
完了済み：〈タスクIDと証拠〉
追加・変更する要件：〈旧条件 → 新条件〉
決定記録：〈decision.md の版〉
残課題：〈条件、担当者、次の調査〉
影響する設計・タスク・テストを先に列挙して更新してください。
その後、影響範囲に含まれる未完了タスク〈ID〉から再開してください。
```

## J. バグの修正依頼

```text
Bugfix Spec を使って〈症状〉を調査してください。
再現条件：〈環境、入力、手順〉
実際の結果：〈ログや画面の証拠〉
期待結果：〈正しい動作〉
維持する動作：〈既存の成功系・互換性〉
まず再現と原因の証拠をまとめ、最小の修正と回帰確認を計画してください。
再現できない場合は、仮説を確定事項にせず不足する情報を示してください。
```
