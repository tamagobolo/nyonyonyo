# 新任シニアエンジニアの導入手順

[入口](../README.md) · [機能の整理](00-kiro-map.md) · [指示文集](04-instruction-playbook.md)

## このガイドでできるようになること

初めて入った既存プロジェクトで、構造・制約・検証手段を説明し、Kiro や開発者へ「対象範囲と完了条件が明確な作業」を依頼できるようにします。最初に作る成果物はコードの全面改修案ではなく、**根拠付きの把握シートと、最初の変更1件の指示書**です。

## 最初の90分の目安

以下の時間は本書の進行案です。アクセス不足、巨大なリポジトリ、起動不能な環境では、時間を超えて調査を続けるか、未確認として担当者へ渡します。90分経過を理解完了とはみなしません。

| 時間 | 確認すること | 手段 | 残すもの |
|---|---|---|---|
| 0–15分 | 事業目的、利用者、開発中の課題、意思決定者 | brief、README、product steering、既存担当者 | 目的・対象外・責任者 |
| 15–35分 | 実行入口、主要モジュール、データと外部境界 | 実コードと依存定義、structure / tech steering | 代表的な1要求の経路と根拠パス |
| 35–50分 | 起動、テスト、CI、既知の失敗 | README・CI の実コマンドを確認して実行 | 基準 SHA、コマンド、結果、環境差 |
| 50–65分 | 壊してはいけない契約と運用条件 | API定義、スキーマ、移行、監視、過去PR | 変更可能・要相談の境界 |
| 65–80分 | 小さな変更の要件と設計候補 | 受入条件と必要な人格スキル | 比較表、採用理由、未解決の質問 |
| 80–90分 | 実装依頼とレビューの方法 | タスク分割、指示文レビュー | 最初の1タスクの依頼文と完了条件 |

## 理解を組み立てる7つの問い

| 問い | 調べる根拠 | 説明できた状態 |
|---|---|---|
| このプロダクトは誰の何を改善するか | README、業務資料、product steering | 利用者・主要ユースケース・成功条件を一文で説明 |
| リクエストはどこから入りどこへ出るか | 実際のエントリポイント、ルータ、ジョブ | 入口→業務処理→データ→外部呼出の1経路を追える |
| データの正本と更新責任はどこか | スキーマ、トランザクション、イベント | 保存先、整合条件、重複・同時更新の扱いを説明 |
| 公開契約は何か | API、イベント、画面、外部連携定義 | 変更が他者に影響する境界を列挙 |
| どう起動し、どう壊れたと分かるか | CI、テスト、起動手順、監視 | 同じコマンドを別の人が再実行できる |
| 誰が何を決めるか | PR規則、担当表、公開手順 | 要件、設計、受入、公開の判断先を識別 |
| 何が未確認か | 矛盾した資料、調査不能箇所 | 仮説・必要な証拠・担当・期限を明示 |

Kiro に描かせた構造図は、その図に記載された関係の根拠ファイルを開いて照合します。「名前からそう見える」モジュールと「実際に呼び出される」モジュールを分けます。動的ロードや環境分岐は、実行時に未確認ならそのまま記載します。

## 最初に Kiro へ渡す調査指示

```text
この既存プロジェクトに新しく参加したシニアエンジニア向けに、現状を調査してください。
対象は〈リポジトリ、ブランチ、基準SHA〉です。
今回の範囲は参照と説明、および指定した把握シートの作成です。
参照：README、既存のAGENTS.md / .kiro/steering、依存定義、CI、主要コード。
代表ユースケース〈1つ指定〉を、入口→処理→データ→外部依存まで追ってください。
各主張にファイルパスとシンボルまたは行を添えてください。
実行確認したこと、コードから推定したこと、未確認を分けてください。
起動・テストのコマンドは既存定義から抽出し、実行前に内容を説明してください。
成果物：docs/project-context.md、優先度付きの質問、最初に試す小さな変更案。
アプリのコード変更や外部サービスの設定変更は今回の範囲に含めません。
```

「調査だけ」という依頼は作業範囲の指定です。操作を強制的に制限する必要がある環境では、別途 Kiro の権限と組織のアクセス設定を確認します。[Permissions](https://kiro.dev/docs/permissions/)

## 的確な指示に必要な8項目

1. **目的**：利用者の振る舞いがどう変わるか。
2. **対象**：リポジトリ、ブランチ、基準 SHA、Spec とタスクID。
3. **根拠**：実ファイル、既存の類似実装、決定済みの設計。
4. **範囲**：変更してよいモジュールと今回は触れない契約。
5. **条件**：成功・失敗・境界値・互換性の受入条件。
6. **裁量**：実装者が決められる部分と相談が必要な変更。
7. **検証**：実在するコマンド、期待結果、必要な証拠。
8. **引継ぎ**：成果物の場所、レビュー担当、残課題の伝え方。

不足した項目をすべて事前質問で埋める必要はありません。コードから確かめられることは調査し、事業上の判断だけを責任者へ質問します。

## 良くない指示を具体化する

| 元の依頼 | 判断できないこと | 具体化した依頼 |
|---|---|---|
| 「Kiroでいい感じに改善して」 | 目的と変更範囲 | 「検索画面で条件を変更したあと、現在の条件が分かるようにする。既存の検索APIを維持し、空結果と通信失敗の表示を受入条件にする」 |
| 「この設計をリファクタして」 | 維持すべき振る舞い | 「重複する入力検証を対象2モジュールに限定して整理する。公開APIとエラー形式は維持し、対象の既存テストが通ることを確認する」 |
| 「全部並列で進めて」 | 依存と編集競合 | 「共有契約を先に確定し、別モジュールで完結するタスクを分ける。統合担当と統合テストを最後に置く」 |

## 初回レビューで自分が見るところ

- 要件にない振る舞いが、人格スキルの提案から混入していないか。
- 既存設計と矛盾する変更を、根拠なしに「ベストプラクティス」で正当化していないか。
- テストが実装の写しにならず、利用者が必要とする結果を確かめているか。
- 更新対象のドキュメントとコードが同じ版になっているか。
- コードを戻せば十分か、データや外部副作用の回復も必要か。

## 導入完了の判定

自分の言葉で代表ユースケースを説明し、任意の受入条件から対応コードとテストへたどれれば、実装指示を出す基礎ができています。把握シートの未確認事項を見ずに断定してしまう場合は、調査の範囲をもう一段狭めて確かめます。

初日の終わりに、把握シート、1件の Spec、最初のタスク依頼、検証の証拠、質問の担当先が残っている状態を目指します。初週はその1件をレビュー・受入まで通し、使わなかった記録項目を削り、実際に迷った判断を手順へ追加します。
